# WeKnora 五大扩展点插件化设计

> 课题一「扩展能力插件化框架」—— 从「扩展点机制」到「插件协议」的架构设计
> 状态：设计稿（部分已落地实现，未落地的部分已逐节标注状态）

---

## 0. 设计立场：先承认一件事

WeKnora 的「扩展点」从来不是一回事，它们只是都被叫「扩展点」。

先划一个范围边界：权威文档 `website-docs/06-development/03-extension-points.md` 列出了 WeKnora 的**九个**扩展点（文档解析、分块、检索、模型接入、联网搜索、数据源、IM 渠道、Agent 工具、对象存储）。**课题一只取其中五类**——数据源、文档解析、网络搜索、模型厂商、检索引擎（分块 / IM / Agent 工具 / 对象存储不在课题一范围内）。本文的「五大扩展点」即指这五类。

证据就在 `docs/wiki/集成扩展/` 的文档里，它们的接入方式**几乎没有任何共同点**：

| 扩展点 | 原生接入方式 | 原生接口形态 |
|---|---|---|
| 数据源 | `Connector → ConnectorRegistry → DataSourceService` | `Connector` 接口：Validate / ListResources / FetchAll / FetchIncremental |
| 文档解析 | Python `BaseParser` + `registry.py`；Go `engine_registry.go` 元数据；docreader gRPC | `BaseParser.parse_into_text`（Python 侧）+ `DocReader: Read/ReadStream`（gRPC） |
| 网络搜索 | 常量 + 元数据 + Provider 实现 + DI 注册 | `WebSearchProvider`：Name / Search（**端点硬编码防 SSRF**） |
| 检索引擎 | 环境变量 + 三层接口 + DI 注册 | `RetrieveEngine` / `RetrieveEngineRepository` / `RetrieveEngineService` |
| 模型厂商 | Provider 注册 + `DetectProvider` | `Provider`：Info / ValidateConfig；Chat / Embed / Rerank / VLM / ASR 各自独立接口 |

**所以本设计的第一个结论，也是贯穿全文的立场：**

> 插件化不是「发明一个统一插件接口，把五类塞进去」。而是做两件正交的事：
> 1. **把五类各自的现有接口，从「编译期注册」外移成「进程外协议」**——每类协议照它自己的特性设计，互不迁就；
> 2. **把五类真正共有的东西（发现、启停、健康、准入、隔离、审计）抽成一个共享控制面**——这层已经存在，且做得不错。

任何「用一个万能 `Invoke` 统一五类」的方案都是错的，它只会把 WeKnora 原本清晰的五条边界糊成一个 `any`。下文每一节，都从「这个扩展点自己的特性」出发。

### 0.1 技术路线选型（课题任务第 1 条的正面回答）

课题任务第一条明确要求「选定技术路线并说明取舍：编译期统一元数据、进程间 gRPC，或其他方案」。本设计的选择与理由如下：

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| 编译期统一元数据（interface + 注册表） | 无跨进程开销、编译期类型安全 | 必须改主仓、重新编译、无法隔离恶意插件、无法跨语言 | 现状，需外移 |
| 进程间 gRPC | 独立仓库、进程隔离、跨语言、可运行时启停 | 序列化/网络开销、生命周期更复杂 | **选定** |
| WASM / 脚本沙箱 | 沙箱强、启动快 | 生态弱、向量库/网络类插件不适用、Go 生态下成本高 | 不选 |

**取舍一句话**：选 gRPC 不是为了「用一个统一协议抹平五类」，而是让每类扩展点都能定义**语义不同的独立 service**，同时把「发现、启停、健康、隔离、审计」这层真正共有的控制面收敛为共享实现。即：

> **统一的是「控制面」，独立的是「协议层」。**

### 0.2 两级架构总览

本设计的目标是一个「大一统插件框架 + 五个细分扩展点框架」的两级结构：

```text
          统一插件框架（大一统控制面，五类 100% 共用）
     Manifest / 发现 / 启停 / 健康 / 准入 / 隔离 / 审计
                              │
        ┌──────────┬──────────┼──────────┬──────────┐
     DataSource  Parser   WebSearch   Model    Retriever
     （拉取+游标）（转换）  （查询）   （生成流） （存储双向）
         每个扩展点一套独立 gRPC service，互不迁就
```

第一层（控制面）五类完全同构；第二层（协议）五类互不重叠。§6 会对两层各自的归属做最终收口。

## 1. 数据源插件：以钉钉为锚点的深度设计

数据源是课题一的验收核心，也是五类里**业务逻辑最厚**的一类。这一节用两个真实案例——PR 2078 的钉钉、现有文档的飞书云盘——把「数据源插件协议到底要承载什么」讲透。

先交代一个权威事实（`10-datasource.md`）：**当前主仓实际注册可用的连接器只有 5 个类型**——`feishu`、`lark`、`notion`、`yuque`、`rss`（feishu/lark 共用一份实现）。而 `connector.go` 的 `ConnectorMetadataRegistry` 里却预留了 Confluence、GitHub、Google Drive、OneDrive、**DingTalk**、Web Crawler、Slack、IMAP 等一堆元数据——**它们有「前端展示用的元数据」却没有「可运行的实现」**。这正是插件化要解决的核心矛盾：钉钉（DingTalk）明明已经被"预告"了，却因为"必须改主仓、提 PR"而迟迟落不了地。

### 1.1 先看一个真实数据源有多复杂（PR 2078 钉钉）

PR 2078 实现钉钉连接器，能力清单大致是：

- 钉钉 OAuth/token 获取；
- `client_id` / `client_secret` / `operator_id` / `base_url` 四类凭证；
- 工作空间列表 → 目录树 → 文档树（**深层懒加载**）；
- 祖先节点解析（文档要知道自己在哪条路径上）；
- 文档 Block 获取 → JSONML/Block **转 Markdown**；
- 标题、时间、URL、文件名处理；
- 全量同步 + 基于 `modified_time` 的增量同步；
- 删除检测；
- **分支级部分失败**（某个目录/文档失败不拖垮整次同步）；
- API 错误、分页、超时、SSRF、响应大小限制。

再看飞书云盘文档（`docs/wiki/集成扩展/飞书云盘数据源接入说明.md`），它揭示的是同一类复杂度的**另一面**：

- 凭证是平台级 OAuth（App ID / Secret），且**权限模型特殊**——飞书要求「把文件夹分享给应用所在的群」，这是平台特有的授权语义，不是简单填个 token；
- 资源树入口是「folder_token」，要能**粘贴完整链接自动提取 token**；
- 文件类型六种（docx/doc、sheet、bitable、file、shortcut、folder），另有三种不支持（mindnote/slides/board），**每种处理方式不同**；
- docx 有「export vs blocks」两种解析路径，代价和产物不同；
- 增量同步以**文件修改时间**为游标，中断续传；
- 源端删除「只计数、不自动删」。

**这两份材料共同说明一件事：数据源扩展点的真正复杂度，不在「接口有几个方法」，而在「平台特有的业务语义」——权限模型、资源树、增量、格式转换、部分失败。** 这些，正是插件协议必须能「装下」，但又**不能替插件去实现**的东西。

### 1.2 逐项映射：钉钉能力 → 插件协议

| PR 2078 的能力 | 插件协议对应 | 结论 |
|---|---|---|
| 凭证（client_id/secret/operator_id/base_url） | `Manifest.config` 中的 secret 型字段（**动态表单待补，见 §7.1**） | ⚠️ |
| OAuth 获取 token | **插件内部**实现 | ✅ |
| 连通性验证 | `DataSourcePlugin.Validate` | ✅ |
| 工作空间列表 | `ListResources(parent_id="")` | ✅ |
| 目录/文档子节点 | `ListResources(parent_id=...)` | ✅ |
| 祖先解析 | `ResolveResourceAncestors` | ✅ |
| 全量拉取 | `FetchAll` / `FetchAllStream` | ✅（已实现） |
| 增量拉取 | `FetchIncremental` + 插件自定义 cursor | ✅（已实现） |
| 删除检测 | `FetchedItem{IsDeleted:true}` | ✅ |
| Block/JSONML 转 Markdown | **插件内部** `renderer` 包 | ✅ |
| 部分失败 | 插件的 warnings / 错误项协议 | ✅ |
| 启停/健康/隔离 | 共享控制面（`PluginManager` + `Runtime`） | ✅ |
| **不修改主仓注册代码** | Manifest 自动发现 | ✅ |

**结论**：接口抽象层面，钉钉完全能由现有数据源插件协议承载，**不需要为主仓增加任何钉钉专属代码**。

> **协议强弱说明（诚实标注）**：当前 v1 数据源协议的方法名是强约束（`Validate`/`ListResources`/`FetchAll`/`FetchIncremental`），但 `config` 参数实际是 `google.protobuf.Struct` 弱信封（见 `pkg/pluginapi/proto/plugin.proto` 的 `DataSourceRequest.config`），字段名与类型要到运行期才校验。这是第一版为换取「跨语言 + 无生成代码耦合」做的取舍；§4 讨论的强类型 `ModelPlugin` 是后续演进方向。数据源插件开发者当前应以 `pkg/pluginapi/datasource.go` 的 Go struct（`FetchedItem`/`Resource`/`DataSourceRequest`）为「事实 schema」，并配合 conformance 测试兜底。

### 1.3 钉钉插件的内部分层（独立仓库）

```
weknora-plugin-dingtalk/
├── plugin.yaml          # 身份/配置/权限/能力声明
├── main.go              # 只负责启动 gRPC 服务
├── auth/token.go        # 钉钉认证与 token（平台特有）
├── client/              # 调用钉钉 API（oauth/workspace/node/document）
├── connector/           # 把钉钉数据转换成插件协议（resources/sync/cursor/errors）
├── renderer/            # Block/JSONML → Markdown（平台特有）
└── README.md
```

分层原则很清晰：**平台特有的（auth/client/renderer）和协议相关的（connector）分开**。`connector` 是唯一「懂插件协议」的层，它把 `client` 拿到的钉钉数据翻译成 `pluginapi.Resource` / `pluginapi.FetchedItem`。

### 1.4 资源树：不透明资源 ID 是正确抽象

钉钉的资源是「工作空间 → 目录 → 文档」的深树。插件协议用**不透明资源 ID**来解耦：

```
dingtalk:v1:<base64(workspace_id + node_id + ancestor_chain + version)>
```

- **前端**只把它当稳定字符串，选中、传回，不理解内容；
- **插件**负责解释它、遍历它、解析祖先；
- **宿主**只负责「资源树的交互骨架」（列出、展开、勾选），不关心这棵树来自钉钉还是飞书。

这正是插件协议要达到的效果：**WeKnora 管理资源树交互，插件负责解释资源 ID**。

### 1.5 增量同步：cursor 必须「按资源、按文档」

飞书和钉钉的增量都不是「一个全局时间戳」能表达的。飞书文档明说「以文件修改时间为游标」，而钉钉存在多工作空间、多选中目录、单文档失败、目录结构变化。

这一判断有权威文档佐证：`10-datasource.md` 里每个连接器的 cursor 结构都不同——飞书 `SpaceNodeTimes`（`resourceID → nodeToken → editTime`）、Notion `PageEditTimes`（`pageID → last_edited_time`）、语雀 `BookDocTimes`（`bookID → docID → content_updated_at`）、RSS「feed 信号指纹 + 内容 SHA-256 双层指纹」。而 `SyncCursor` 的宿主侧统一外壳只有两个字段：`LastSyncTime` + `ConnectorCursor map[string]interface{}`（**连接器自定义结构**）。

所以钉钉插件的 cursor 应该是「按资源、按文档」的结构，而非全局 `last_sync_time`：

```json
{
  "version": 1,
  "synced_at": "2026-08-24T10:00:00Z",
  "resources": {
    "dingtalk:v1:workspace-a": {
      "nodes": {
        "node-1": { "modified_time": "2026-08-24T09:30:00Z" }
      }
    }
  }
}
```

插件协议里 cursor 是「插件自定义 JSON」，因此这种结构可以直接表达。**但这里有一个框架层必须诚实标注的语义问题**（见 §6.1）：cursor 到底表示「插件已成功读取」还是「宿主已成功入库」。

### 1.6 文档转换：必须放插件内部，这是数据源扩展点的「特性」

钉钉的 JSONML/Block 转 Markdown、飞书的 docx export vs blocks 选择——这些是**平台特有格式转换**。插件最终只返回统一的 `FetchedItem`（`ExternalID` / `Title` / `Content []byte` / `ContentType` / `FileName` / `URL` / `UpdatedAt` / `Metadata` / `IsDeleted` / `SourceResourceID`，字段与 `internal/types/datasource.go` 的 `FetchedItem` 对齐），宿主后续只做「解析 → 分块 → embedding → 索引」。

**这是数据源扩展点最重要的边界**：宿主**永远不关心**内容原本是钉钉 Block、飞书 docx 还是 Confluence 的 storage format。谁对接平台，谁负责转换。

> **一个被现有实现反复印证的边界**：权威文档 `10-datasource.md` 明确——「`IsDeleted=true` 的条目只累加计数，**刻意不真正删除知识库条目**（防止连接器误判或重新配置导致意外数据丢失，用户需在 KB UI 显式删除）」。也就是说，「源端删除只计数、不自动删」不是飞书独有，而是**所有数据源连接器的宿主侧通例**。插件只需如实上报 `IsDeleted`，删不删由宿主策略决定——这条边界划清后，插件协议就无需为「删除语义」再引入任何平台特判。

## 2. 文档解析插件：从「本地 + 远程混合」这个特性出发

> **状态**：协议已定义并实现（`ParserPlugin` service 已存在于 `plugin.proto`），有模板基础；尚无真实外部解析插件的端到端验证。

解析扩展点有一个它独有的特性：**真正的「解析器」在 Python docreader 侧，Go 侧只有一层元数据注册**。这正是它和数据源、搜索最不同的地方——它不是 Go 接口，而是一个**已经跨进程的 gRPC 微服务**。

权威文档 `website-docs/06-development/03-extension-points.md` 与 `03-features/03-document-parsing.md` 揭示的真相是：

1. **真正的解析器扩展点是 Python 的 `BaseParser`**（`docreader/parser/base_parser.py`）：抽象方法只有一个 `parse_into_text(content: bytes) -> Document`，注册点在同目录的 `registry.py`（`ParserEngineRegistry`，维护「引擎名 → {文件扩展名 → Parser 类}」两级映射，`_build_default_registry()` 注册 `builtin`/`markitdown`/`opendataloader` 三个引擎）。

2. **docreader 本身就是一个 gRPC 微服务**：`docreader/proto/docreader.proto` 定义 `service DocReader { rpc Read; rpc ReadStream; rpc ListEngines; }`，监听 `50051`。Go 侧 `internal/infrastructure/docparser/grpc_parser.go` 优先走 `ReadStream`，遇到旧版回退 unary `Read`。**所以解析引擎「天然就是进程外的」——只是它现在被 hardwire 到 docreader 这「一个」进程，而不是可插拔的多进程。**

3. **Go 侧的 `engine_registry.go`（`EngineRegistration`）只是「元数据 + 可用性检查 + Reader 工厂」的注册层**，`CheckAvailable(docreaderConnected, overrides)` 问的是「这个引擎在这个 build / 这个租户下能不能跑」；真正的 parse 逻辑在 Python 侧。而且 `ListEngines` 已不再由 Python 提供，改由 Go 侧 `docparser.ListAllEngines` 管理。

所以解析插件化要面对的是一个**特殊现状**：插件化对象是「Python 侧的解析器实现」，而 Go 侧已经有一套 gRPC 协议（`DocReader`）。设计上存在两条路线：

- **路线 A（复用 DocReader）**：把新的解析引擎实现为 docreader 里可动态加载的 `BaseParser`，或独立部署的 gRPC 服务实现 `DocReader` 协议——协议复用，但引擎仍受 docreader 进程管辖。
- **路线 B（另立 ParserPlugin）**：在统一插件框架里为解析器定义独立协议：

```proto
service ParserPlugin {
  rpc Parse(ParseRequest) returns (ParseResponse);
}
```

- `ParseRequest`：`file_content` + `file_name` + `file_type` + `options`（对应 docreader 的 `ReadRequest` 字段）。
- 无状态、无 cursor、无 Validate（可用性在注册期表达）、一次 Parse 一次结果。

**当前 `plugin.proto` 里已实现的 `ParserPlugin` 是路线 B，它与现有 `DocReader` 协议字段高度重合**（`ParserRequest` 的 `file_content`/`file_name`/`file_type`/`parser_engine_overrides` 基本照搬 `ReadRequest`）。这是有意的：让「解析器」也能进入统一插件框架的生命周期与隔离管理。但必须诚实标注：**路线 B 与现有 docreader 是两条并存路径，尚未证明谁更该成为主路径**——这是解析插件五类里「最该在下一阶段想清楚」的协议边界，而不是已经定型。

**反思**：解析插件是五类里「最接近数据源插件，又最不该复用数据源协议」的一类——它连「Fetch」这个概念都没有，只有「给我文件，还你文档」。任何试图让它复用 `FetchAll` 的设计都是错误的。

## 3. 网络搜索插件：从「端点硬编码」这个特性出发

> **状态**：协议已定义并实现（`WebSearchPlugin` service 已存在于 `plugin.proto`），有模板基础；尚无真实外部搜索插件的端到端验证。

搜索扩展点有一个**它独有、别的扩展点都没有**的特性：SSRF 防护。

`docs/wiki/集成扩展/添加网络搜索引擎.md` 第一句就写：

> 「搜索引擎的 API 端点**硬编码**在代码中，不向用户暴露 BaseURL，从源头消除 SSRF 风险。」

`11-web-search.md` 进一步确认：现有 **9 个引擎**（duckduckgo / google / bing / tavily / ollama / baidu / searxng / keenable / zhipu）里，**除 SearXNG 外所有端点都硬编码、租户不可配置**（源码注释原文「Not configurable by tenants — prevents SSRF」）；SearXNG 是唯一允许自填 `base_url` 的（自托管实例），需过 SSRF 校验。

这是搜索和数据源**最关键的分歧**：

| 维度 | 数据源 | 网络搜索 |
|---|---|---|
| 端点 | 用户可填（钉钉 base_url、飞书 folder_token） | **硬编码，不暴露**（仅 SearXNG 例外） |
| SSRF | 需要 base_url 校验（§1.1 提到 SSRF 限制） | 端点固定，天然免疫 |
| 凭证 | 平台 OAuth，宿主持有 | api_key 落库（AES-GCM），**调用时按租户参数实例化** |
| 状态 | 有 cursor 增量 | 无状态，一次一询 |

所以搜索插件协议极简：

```proto
service WebSearchPlugin {
  rpc Search(SearchRequest) returns (SearchResponse);
}
```

- `SearchRequest`：`query` + `max_results` + `include_date` + `api_key` + `engine_id`（+ `proxy_url`）。
- 凭证模型的精确表述（修正原「随请求传」的含糊）：搜索凭证不是「用户每次搜索临时传」，而是**租户配置落库**（`web_search_providers` 表，AES-GCM 加密，经 `/credentials` 子资源修改）。现有 `Registry.CreateProvider(providerType, params)` 是「**按租户参数在调用时实例化 Provider**」，`params` 里带上解密后的 `api_key`——所以一个搜索插件进程天然服务多租户，凭证保持在 **factory 边界**，不驻留在 Provider 实例里。插件化后这个语义不变：**插件进程无状态、不持有凭证，凭证随每次调用传入**。

**搜索插件不需要** `Validate`、不需要资源树、不需要 cursor、不需要流式——它不是「拉取器」，是「查询器」。这是它和数据源的本质区别。

## 4. 模型管理插件：从「五类模型 + 26 厂商 + 1 本地」这个特性出发

> **状态**：本节为**纯设计稿**。`ModelPlugin` service 尚未写入 `plugin.proto`，扩展类型已预留但无实现。下文的 `ModelPlugin` proto 是建议目标，不是现状。

模型厂商是五类里**厂商最多、凭证差异最大、且有流式生成**的一类。

`internal/models/provider/provider.go` 揭示了两个特性：

1. **26 个远程 Provider + 1 个本地 Ollama**（`source=local`，独立于 Provider 注册表）。凭证形态天差地别：OpenAI 一个 `api_key`；Azure OpenAI 是 `api_key + endpoint + api_version + deployment`；本地 Ollama **可能无凭证**。（课题首页「27 个模型厂商」即此口径：26 remote + 1 local。）
2. **`DetectProvider` 靠 BaseURL 猜厂商**——这暴露了「厂商身份」是隐含在 URL 里的，插件化后应该由 Manifest 显式声明。

更重要的是，模型能力分**五种语义不同的接口**（`internal/types/model.go` 的 `ModelType` 枚举，而非「三类」）：

```
KnowledgeQA(chat)  Chat.Chat（非流式）/ Chat.ChatStream（流式生成）
Embedding          Embedder.Embed / BatchEmbed（高频批量向量化）
Rerank             Reranker.Rerank（短同步排序）
VLLM               VLM.Predict(imgBytes, prompt)（图片理解）
ASR                ASR.Transcribe(audioBytes, fileName)（语音转写）
```

**设计决策**：`ModelPlugin` 用 **capability 分组**，而非拆成五个 extension_type。因为一个厂商往往同时提供多类模型（OpenAI 五类全支持），拆成五个插件会让「同一个 OpenAI」注册五次。capability 分组让插件「可分可合」：

```proto
service ModelPlugin {
  // chat 能力
  rpc Chat(ChatRequest) returns (ChatResponse);
  rpc ChatStream(ChatRequest) returns (stream ChatStreamResponse);

  // embedding 能力
  rpc Embed(EmbedRequest) returns (EmbedResponse);
  rpc BatchEmbed(BatchEmbedRequest) returns (BatchEmbedResponse);

  // rerank 能力
  rpc Rerank(RerankRequest) returns (RerankResponse);

  // vllm 能力（图片理解）
  rpc PredictVLM(VLMRequest) returns (VLMResponse);

  // asr 能力（语音转写）
  rpc Transcribe(ASRRequest) returns (ASRResponse);

  // 动态模型清单（厂商上新模型不依赖宿主改代码）
  rpc ModelInfo(ModelInfoRequest) returns (ModelInfoResponse);
}
```

模型插件区别于其它四类的四个特性：

1. **流式是「生成流」，不是「拉取流」**。数据源的 `FetchAllStream` 是「宿主拉一批给一批」，模型的 `ChatStream` 是「插件持续吐 token 直到结束」，反压/取消/错误语义不同，必须分开建模。
2. **凭证最高敏感 + 长连接池**。chat 流式和 embedding 高频，决定了 model 插件的凭证必须「宿主持有、按 model_id 解析、InvocationContext 只传 model_id 不传 key」（和 web-search 的「落库、调用时按租户传入」**恰好相反**——model 的凭证连调用时都不出宿主，插件只拿到 model_id），连接则必须常驻复用。
3. **计费/用量是新维度**。其它四类没有「token 计数、缓存命中、费用」概念，模型天然有。协议预留 `usage` 字段做**透传**（插件上报、宿主记录），结算在宿主策略层，不在协议层。
4. **`ModelInfo` 让厂商可插拔**。否则每上新模型，宿主就要硬编码一次模型列表。

## 5. 检索引擎插件：从「三层接口 + 强状态」这个特性出发

> **状态**：本节为**纯设计稿**。`RetrieverPlugin` service 尚未写入 `plugin.proto`，扩展类型已预留但无实现。下文的 proto 是建议目标，不是现状。

检索引擎是五类里**唯一有强状态**的一类，也是**唯一不强制进程外**的一类。

`05-retrieval-engines.md` 揭示了它的真实分层（比「三层」更细的四层）：

```
RetrieveEngineRepository   每个后端实现：EngineType / Support / Save / BatchSave / Retrieve / DeleteBy* / CopyIndices / ...
KVHybridRetrieveEngine     把 Repository 包装成 RetrieveEngineService，Index 时算 embedding 写入
CompositeRetrieveEngine    组合模式：写操作广播到所有成员，检索按 RetrieverType 路由
RetrieveEngineRegistry     双索引：byEngineType（RETRIEVE_DRIVER env store）+ byStoreID（vector_stores 表实例级）
```

加上 Doris 集成要点暴露的复杂度：MySQL 协议 + HTTP Stream Load、每维度一张表、HNSW 异步构建、BM25 sparse vector、批量字段更新——**每个引擎的存储协议、索引构建、分数语义都不同**。

检索引擎区别于其它四类的特性：

1. **强状态 + 双向数据流**。其它四类要么「宿主拉」（datasource）、要么「单次投喂」（parser/search）、要么「单次请求」（model）。检索引擎是「宿主持续写 + 持续查」，索引是长驻状态，`CreateIndex/DropIndex/DeleteChunks` 这类「管理索引状态」的方法，其它四类一个都没有。
2. **连接最重**。向量库连接是昂贵资源，必须持久复用、连接池化、健康探活，比 model 的连接更「重」。
3. **数据模型是 chunk 视图，不是文档视图**。检索最小单元是 chunk（带 embedding + knowledge_id/chunk_id/tag_id/score），和数据源的 `FetchedItem`（文档级）完全不是一回事。
4. **检索参数必须留扩展位**。现有 `RetrieveParams.AdditionalParams map[string]interface{}` 说明「不同引擎需要不同参数」，协议不能做死成固定字段。
5. **强状态的具体体现：注册表要「按需重建」**。`05-retrieval-engines.md` 记录了 rehydrate 机制——启动时向量库不可用就不进 `byStoreID`，之后用 `GetOrLoadByStoreID` 现场构建（`singleflight` 合并并发、`EngineBuildTimeout` 10s、失败 `rebuildCooldown` 30s、`storeGen` 代际计数防竞态）。这种「长驻状态 + 故障自愈」的复杂度，是其它四类进程外插件完全不需要面对、而 retriever 插件必须回答的。

**一个对协议设计至关重要的边界**（来自 `05-retrieval-engines.md` §5）：WeKnora 的混合检索**永远是宿主侧统一 RRF 融合**——「无论引擎自身是否提供混合检索，向量与关键词各自独立检索，按 rank 加权合并」。这意味着 `RetrieverPlugin.Search` **只应暴露单模检索**（向量 OR 关键词），混合融合是宿主的职责，插件不该也不该被要求实现混合。这条边界划清，retriever 插件协议才能保持最小。

所以检索引擎插件协议是「存储型」：

```proto
service RetrieverPlugin {
  rpc CreateIndex(CreateIndexRequest) returns (CreateIndexResponse);
  rpc UpsertChunks(stream UpsertChunksRequest) returns (UpsertChunksResponse);
  rpc DeleteChunks(DeleteChunksRequest) returns (DeleteChunksResponse);
  rpc DropIndex(DropIndexRequest) returns (DropIndexResponse);

  rpc Search(RetrieveRequest) returns (RetrieveResponse);
  rpc BatchSearch(BatchRetrieveRequest) returns (BatchRetrieveResponse);
}
```

**关键边界**：检索插件接收的是「已经 embedding 好的向量」，**它不做 embedding**——embedding 是 model 插件的职责。这条边界划清楚，retriever 和 model 才能自由组合（任意 embedder × 任意 retriever）。

**诚实标注（这是五类里风险最高的一类）**：数据源/解析/搜索进程外化是「明显净收益」，但检索引擎进程外化引入「跨进程向量传输 + 索引一致性」两大成本。所以本设计对 retriever 的态度是：**协议先定义清楚，落地优先级最低，且第一阶段允许「内置 driver 直连」与「外部插件」两种模式并存**——它是五类里唯一「不强制进程外」的扩展点。

## 6. 共性收敛：什么属于「插件框架」，什么属于「扩展点自己」

讲完五类的特性，回到「大一统」这个前提，把边界画死。

### 6.1 属于「插件框架」的（五类 100% 共用，已经存在）

| 框架能力 | 说明 |
|---|---|
| Manifest（plugin.yaml） | `id/version/extension_type/protocol_version/weknora_version` 五类同构 |
| 发现 / 装载 / 启停 / Drain / Fencing | `PluginManager` + `Runtime`，与 extension_type 无关 |
| 准入（并发控制） | 五类都怕被打爆 |
| 网络隔离 + 审计 | 五类都可能是恶意的 |
| `config`（settings + credentials 声明） | **结构同构**；普通 settings 已动态渲染，secret 型凭证表单待补（见 §7.1） |
| InvocationContext | 五类共用，但 payload 不同（见 6.2） |

### 6.2 属于「扩展点自己」的（五类互不重叠）

| 维度 | 数据源 | 解析 | 搜索 | 模型 | 检索 |
|---|---|---|---|---|---|
| 业务 service | DataSourcePlugin | ParserPlugin | WebSearchPlugin | ModelPlugin | RetrieverPlugin |
| 数据流形态 | 拉取（批量+游标） | 转换（单次） | 查询（单次） | 生成（流式） | 存储（双向） |
| 状态模型 | cursor 续传 | 无 | 无 | 流式生成态 | 索引强状态 |
| 凭证模型 | 宿主持有，按 ds_id | 引擎级 overrides | 落库，调用时按租户传入 | 宿主持有，按 model_id | 宿主持有连接串 |
| 是否需 Validate | ✅ | ❌（注册期 CheckAvailable） | ❌ | ✅ | ✅（即 Health） |

### 6.3 一个必须诚实标注的框架语义缺口

§1.5 提到的 cursor 语义问题，这里说透：**cursor 到底是「插件已成功读取」的 checkpoint，还是「宿主已成功入库」的 checkpoint？**

当前是前者。所以存在风险链：插件 emit 了 item → 宿主存了 cursor → 后续解析/入库失败 → 下次增量跳过它。

这不是钉钉业务问题，而是**插件同步协议与宿主 ingestion 之间的语义问题**。它不阻塞课题一验收（验收要求「源端只变一个文件时只有该文件被重新处理」，这个已满足），但生产级需要明确「入库失败的文档如何重新加入待处理集合」。本设计诚实标注为「下一阶段」，不在课题一内解决。

## 7. 两个「通用能力缺口」的现状更新

相对最初方案，这两个缺口的现状是：

1. **外部插件凭证的动态表单** —— **尚未完全落地**。当前已实现：`config`（即实现的配置字段名）中的普通 settings 字段（`type: directory`、`string[]` 等）已由前端 `DataSourceEditorDialog.vue` 动态渲染。**尚未实现**：secret 型凭证字段（`client_id`/`client_secret`/`operator_id` 这类需密码框、编辑时不误清空、脱敏回显的字段）的动态表单。所以「钉钉的凭证表单」这一步，前端仍需补通用的 secret 字段渲染，尚未零代码支持。

2. **联网插件的受控出站（egress）运行时** —— **仍未实现**。现状三种状态：

| 运行方式 | 钉钉能否运行 | 安全级别 |
|---|---|---|
| `ProcessRuntime` + network allowlist SDK | 可以 | 开发态 / 软约束 |
| `DockerRuntime` + `network none` | **不能**（访问不了 api.dingtalk.com） | 硬隔离，但只适合不联网插件 |
| Docker/OCI + 受控 egress proxy | **尚未实现** | 目标生产方案 |

所以最准确的一句话结论是：

> **钉钉的「业务架构」已能由现有插件协议完整承载，不需要改主仓；但钉钉要「生产级安全地访问 api.dingtalk.com」，还差一个「受控 egress 运行时」——这是插件框架的通用能力，不是钉钉专属问题。**

**同时必须划清一条验收边界，避免误读**：

- 课题验收第 2 条要求的是「**声明不联网**的插件，运行期实际无法出站、尝试联网会被拦截并记录」——这条**已经满足**：`network: none` 插件在 Docker 模式下 `--network none` 硬隔离，SDK Guarded Client 拦截并写 `plugin_audit`，宿主 Runtime 捕获 stderr 补齐可信信息后落 `AuditSink`。
- 尚未实现的「受控 egress 运行时」，是给**声明要联网**（如钉钉 `network: api.dingtalk.com`）的插件提供「经白名单代理出站」的能力。这**超出课题验收范围**，属于生产级加分项，而非验收必需。

## 8. 落地路径（按风险与收益排序）

> 先明确验收基线：课题四条验收中，**第 1 条（独立仓库插件无需改主仓即可装载并完成同步）、第 3 条（增量同步只重处理变更文件）已由 LocalDir 插件达成**；第 4 条（他人仅凭文档实现最简插件）已有模板与文档，但需一次正式盲测闭环。第 2 条（不联网插件出站被拦截并记录）已由 `network: none` + Guarded Client + stderr 审计达成。下表是**超出验收的后续加分项**，按风险与收益排序：

| 优先级 | 事项 | 理由 |
|---|---|---|
| **P1** | 完成「联网插件受控 egress 运行时」 | 让钉钉这类联网数据源生产可用，是**加分项**（验收只要求「不联网」被拦截） |
| **P2** | 用钉钉插件做一次端到端验证 | 以 PR 2078 为蓝本拆出独立插件，证明「复杂数据源」也能走通。**注意：LocalDir 已满足验收（课题明确列本地目录为可选项），钉钉是超出验收的说服力增强，而非验收必需** |
| **P3** | 补齐 parser / search 真实示例插件 | 协议已存在，只差像 LocalDir 的端到端验证 |
| **P4** | 设计并实现 `ModelPlugin` | 全新协议，价值高（26 厂商 + 1 本地最该可插拔） |
| **P5** | 设计 `RetrieverPlugin` | 协议优先，落地最后，允许内置/外部并存 |

**关于 retriever 排 P5 的正面回应**：课题背景专门点名「检索引擎新增向量库后端仍需修改核心工厂文件」，恰恰说明它**最需要插件化**。但它的进程外化成本也是五类里最高的（跨进程向量传输 + 索引强一致性），因此采取「协议先冻结、落地放最后、过渡期内置 driver 直连与外部插件并存」的策略——这是**先难后易的优先级取舍，不是回避**，也不影响「大一统框架」在控制面层已把 retriever 纳入统一生命周期管理。

## 9. 一句话总结

> WeKnora 的五大扩展点，共享的只有「控制面」（发现、生命周期、准入、隔离、审计），而「协议层」必须各自独立——因为它们在**数据流形态（拉取 / 转换 / 查询 / 生成 / 存储）、状态模型（游标 / 无 / 无 / 流式 / 索引）、凭证模型（宿主持有 / 引擎级 / 落库按租户传 / 宿主持有 / 连接串）**上几乎两两不同。要判断「能不能设计出钉钉插件」，答案是：**接口抽象上完全可以，且无需改主仓；真正缺的只是一个通用的「受控 egress 运行时」**——而这个缺口属于框架，不属于钉钉。
