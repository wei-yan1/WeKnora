## 1. 课题背景与问题定义

### 1.1 原任务书背景

数据源连接器、文档解析引擎、网络搜索引擎、模型厂商是 WeKnora 的四类扩展点。目前各自有一套注册机制，风格互不统一，并且**全部是编译期注册**。任何人想给 WeKnora 加一个新数据源，都必须改主仓代码、提 PR、等待合入。检索引擎（向量库后端）新增一个后端仍需修改核心的工厂文件。社区规模越大，这条路越走不动。

### 1.2 [补充] 导师讲话里的深层动机

- WeKnora 最初的设想是"**我们提供接口，各开发者适配这套接口接入**"，接口化方向是对的。
- 但随着项目发展，**主仓库代码体量越来越大、维护成本越来越高**，继续把所有连接器/解析器/provider 都收在主仓里不可持续。
- 期望的方向是：**插件可以在主仓库之外维护**——通过一个**新接口**或**应用层独立包**接入。
- 导师明确：**这块还没有完整方案，技术路线选型需要大家去考虑**，因此本课题的产出应包含一份"选定路线 + 取舍论证"。
- 导师点名的必备件：**插件 manifest（描述文件）**、**统一的注册/管理/健康检查流程**、**脚手架**、**详细的开发文档**。
- 验收导向上，导师额外强调两点：**(1) 声明式网络权限与安全拦截**；(2) **通过插件形式把新数据真正导入知识库的闭环**。

### 1.3 现状盘点（基于代码，作为方案的事实基础）

| 扩展点 | 接口/注册位置 | 现状 | 痛点 |
|---|---|---|---|
| 数据源连接器 | `internal/datasource/connector.go`；装配于 `internal/container/container.go::initConnectorRegistry` | `Connector` 接口最成熟（`Validate`/`ListResources`/`ResolveResourceAncestors`/`FetchAll`/`FetchIncremental`），并有可选 `StreamingConnector`（`FetchStream`+`StreamHandler`+`Checkpoint`）支持流式与断点续传 | 每加一个连接器都要在 `container.go` 手写 `registry.Register(...)`；`ConnectorMetadataRegistry` 是硬编码 map，前端展示的元数据也写死 |
| 文档解析引擎 | `internal/infrastructure/docparser/engine_registry.go` + `engines.go` | `EngineRegistration` 接口 + `RegisterEngine()` 在 `init()` 里调用 | 纯编译期；但已存在"本地引擎 + 远程 Python docreader 经 RPC 的 `ListEngines` 自动发现"混合模型，是可复用的先例 |
| 网络搜索引擎 | `internal/infrastructure/web_search/registry.go` | `Registry` + `ProviderFactory`（`Register(id, factory)`） | 编译期注册，无运行时装载 |
| 模型厂商 | `internal/models/provider/provider.go` | `Provider` 接口 + 全局 `Register()`，26+ 个 provider 文件各有一个 `init()` | 新增 provider 必须改主仓并重新编译 |
| 检索引擎/向量库 | `internal/container/container.go` | 硬编码 `if slices.Contains(retrieveDriver, ...)` 逐支 `registry.Register(...)` | 导师所说的"改工厂文件"问题在此最直接 |

**统一结论**：四类扩展点**接口定义不统一**（有的返回 `error`，有的不返回；有的用 map，有的用 slice），**全部编译期/装配期注册**，无统一的生命周期（启停/健康检查）抽象，无版本兼容与权限声明。

## 2. 目标与验收标准

### 2.1 原验收标准（保留）

1. 位于主仓之外独立仓库的插件，无需修改主仓代码即可装载，并完成一次完整的数据同步。
2. 插件声明不联网时，运行期实际无法发起出站请求，尝试联网会被拦截并记录。
3. 示例插件的增量同步正确：源端仅变更一个文件时，只有该文件被重新处理。
4. 他人仅依据文档即可独立实现一个可运行的最简插件。

### 2.2 [补充] 导师新增/强调的验收点

5. **[补充]** 插件独立于主仓库（与第 1 条同源，但强调"独立仓库、独立维护、独立版本"）。
6. **[补充]** 声明式网络权限：插件**声明不需要网络**，却**发起了网络请求**时，必须被**拦截并记录**（安全因素）——这是对第 2 条的强化与实现要求。
7. **[补充]** 插件正确性闭环：通过插件完成一次**真实的数据源同步**，并把新获取的数据**导入知识库**（而非仅做桩/空转）。
8. **[补充]** 方案设计需**参考现有文档**（`docs/`、`internal/datasource/*.md`、ADR 等）。

## 3. 技术路线选型与取舍（核心补充）

### 3.1 候选方案

| 方案 | 说明 |
|---|---|
| A. 编译期统一元数据 | 收敛四类扩展点为统一接口 + `init()` 注册 + 统一 manifest 常量，仅做"标准化"，不引入进程外装载 |
| B. Go 原生 `plugin` 包 | 动态加载 `.so` |
| C. 进程间 gRPC | 独立插件进程，通过 gRPC 握手接入（借鉴 HashiCorp go-plugin，做轻量裁剪） |
| D. WASM 沙箱（wazero/wasmtime） | 插件编译为 `.wasm`，宿主内嵌运行时加载 |
| E. 子进程 + stdio JSON-RPC（LSP 风格） | 轻量文本协议 |

### 3.2 逐项取舍

**B（Go plugin）——否决。**
- 仅 Linux/macOS 可用，**Windows 不支持**；而导师提到的"桌面版本地文件目录"场景天然要求跨平台。
- 主程序与插件必须使用**完全一致的 Go 版本与依赖哈希**，耦合极强，调试体验差，社区实践普遍认为不可用于公开插件生态。

**A（仅编译期统一）——不满足验收，不能单独作为结论。**
- 它无法满足验收第 1 条"独立仓库、不改主仓即可装载"（编译期注册必然要改主仓 import）。
- 但 A 的价值在于：**统一抽象是任何方案的前置工作**，可作为"内置插件通道"保留。

**E（stdio JSON-RPC）——轻量但工程债高。**
- 跨语言、跨进程、启动成本低；但类型安全、流式传输、双向健康检查、错误语义都要自己造轮子，长期维护成本不低。

**D（WASM）——最理想的"网络拦截"载体，但不建议本期主路线。**
- 沙箱能**从指令层剥夺网络 syscall**，天然满足"声明不联网就物理无法出站"，是验收第 2 条的"最优解"。
- 但 Go→WASM 在 `net/http`、goroutine、文件 IO 上受限，现有连接器（飞书/Notion 等大量 HTTP 调用 + 复杂增量逻辑）迁移成本极高。定位为**远期或专项加固**。

**C（进程间 gRPC）——推荐主路线。**
- 满足"独立仓库、独立编译、不改主仓"：插件是独立进程，宿主按 manifest 发现并拉起。
- **进程隔离**：插件崩溃不拖垮主服务，启停/健康检查边界清晰。
- **成熟的健康检查协议**（`grpc_health_v1`）、流式 RPC（可直接承载现有 `FetchStream`/`Checkpoint` 增量语义）。
- 协议中立，未来可跨语言。
- 代价：序列化开销、运维复杂度、跨进程调试成本；增量同步的流式/checkpoint 语义需在 proto 层重新定义。

### 3.3 推荐路线：统一抽象 + 双装载通道

```
统一插件描述文件（plugin manifest）
        │
        ▼
统一插件生命周期抽象（Load → Configure → Start → HealthCheck → Stop）
        │
        ├── 内置通道：编译期注册（现有扩展点收敛为"内置插件"）
        │
        └── 外部通道：进程间 gRPC（独立仓库插件，运行时装载）
```

- **本期落地**：以"统一 manifest + 统一生命周期抽象"为骨架，**外部插件走 gRPC**，把现有四类扩展点**收敛到同一套抽象**，跑通数据源插件作为示范。
- **"内置扩展与外部插件走同一套装载、启停与健康检查流程"**（原任务书要求）由"统一抽象 + 两种通道实现同一接口"来满足，而非两套并行逻辑。

## 4. 插件描述文件（manifest）设计

统一使用一个声明式描述文件（建议 `plugin.yaml`，可读性优于 JSON）。示例（本地文件目录数据源插件）：

```yaml
id: datasource.local-dir
name: 本地文件目录
version: 0.1.0
description: 同步本地目录下的文档（桌面版场景）

# 扩展类型：connector | parser | search_engine | model_provider | retriever
extension_type: connector

# 框架协议版本（语义化范围）
api_version: "1.x"

# 适配的 WeKnora 版本范围
compatibility:
  weknora: ">=0.5.0 <0.7.0"

# 入口：外部插件为可执行命令/路径；内置插件留空
entrypoint:
  command: ["localdir-plugin", "serve"]
  protocol: grpc

# 配置项（JSON Schema，用于前端表单与校验）
config_schema:
  type: object
  required: ["root_dir"]
  properties:
    root_dir:
      type: string
      title: 根目录
    include_pattern:
      type: string
      default: "*.md,*.txt,*.pdf"
    api_token:
      type: string
      format: password      # 敏感项

# 权限声明（见第 6 节安全模型）
permissions:
  network: false            # 不联网
  filesystem:
    read: ["${root_dir}"]
  data:
    tenants: ["self"]       # 仅本租户

# 能力声明（用于增量同步判定与 UI 展示）
capabilities: [incremental, streaming]

# 健康检查方式：grpc | local
health: grpc
```

**关键设计点**：
- `extension_type` 决定插件被归入哪类注册表；
- `api_version` + `compatibility` 解决"适配版本范围"与升级兼容；
- `config_schema` 用 **JSON Schema** 声明配置项，宿主据此渲染表单、做前置校验；
- `permissions` 声明**联网能力、可访问文件、可访问数据（租户/知识库）范围**；
- `capabilities` 声明增量/流式/删除同步等能力，替代现状里硬编码的 `ConnectorMetadata.Capabilities`。

## 5. 统一注册与管理

### 5.1 统一生命周期接口

```go
type Extension interface {
    Info() ExtensionInfo              // 与 manifest 一致
    Configure(cfg map[string]any) error
    Start(ctx context.Context) error
    HealthCheck(ctx context.Context) error
    Stop(ctx context.Context) error
}

// 数据源类扩展再实现具体业务接口（Connector/Provider/...），
// 与现有 Connector 接口兼容，降低迁移成本。
```

### 5.2 装载流程

```
发现（扫描插件目录/内置表）
  → 解析并校验 manifest
  → 校验 api_version 与 compatibility
  → 校验权限声明（权限不得超出宿主允许范围）
  → 装载（内置=构造 / 外部=gRPC 拉起+握手）
  → Register 入对应类型注册表
  → Configure + Start
  → HealthCheck 通过后标记 ready
  → 失联/异常 → unhealthy → 摘除 + 告警 + 按策略重启
```

### 5.3 启停与健康检查

- **内置插件**：构造/析构，`HealthCheck` 走本地 ping。
- **外部插件**：宿主管理子进程生命周期（拉起、优雅退出、崩溃重启）；`HealthCheck` 走 `grpc_health_v1`，周期探测，失败即从注册表摘除并记录。
- 统一对外暴露一个 `PluginManager`，四类扩展点共用。

### 5.4 [补充] 脚手架

本期提供可直接复制的模板工程（目录结构 + `plugin.yaml` + SDK Handler +
README + 可运行的最小示例），配合本开发指南完成 `build`、`run` 和打包。
`weknora-plugin init/build/package` CLI 属于后续便利工具，不作为本期已经
实现的交付物；本期验收以模板和文档能否独立完成插件为准。
目标：**别人照着文档 + 模板即可独立写出最简插件**。

## 6. 声明式网络权限与安全（导师重点）

把"能否联网"从"代码行为"提升为"声明 + 强制"。分三档强度，诚实说明边界：

- **L1 声明式契约（软约束，本期必做）**：manifest 声明 `permissions.network`；宿主向插件**注入受控的出口 HTTP client**（插件不自行 `http.NewClient`，而是从框架获取带权限校验的 client）。越权请求被拒绝并**写入审计日志**。
- **L2 进程级隔离（硬约束，验收第 2 条的关键）**：外部 gRPC 插件运行在**无网络的容器/网络命名空间**中，从 OS 层禁网；插件声明需要联网时，宿主通过**受控转发通道**代理其合法出站请求。这样"声明不联网 → 实际无法出站"，而非仅靠自觉。
- **L3 运行时沙箱（WASM，远期加固）**：指令层无网络 syscall，最强隔离。

> **取舍结论**：验收第 2 条要求"实际无法发起出站请求、尝试联网被拦截并记录"。要真正"无法发起"，需落到 **L2**（进程级网络隔离）+ L1 的**审计记录**。本期以 L1+L2 满足验收；L3 作为远期方向写入 roadmap。

## 7. 示例插件与增量同步正确性

**示例选择**：本地文件目录数据源（桌面版场景，导师建议的选项之一），做成**外部 gRPC 插件**，最能验证"独立仓库、不改主仓"。

- **复用现有增量语义**：把 `FetchIncremental` + `SyncCursor` + `StreamHandler/Checkpoint` 的成熟语义映射到 gRPC **流式 RPC**。
- **变更检测**：以文件 `mtime + size + hash` 作为指纹，`SyncCursor` 记录上次扫描水位；对每个文件比对指纹，**只对变更项 `Emit`**。
- **验收第 3 条落地**：单测构造"仅一个文件变更"的场景，断言只有该文件被重新处理（其余文件不产生 ingest）。
- **验收第 7 条落地**：示例插件同步到的 `FetchedItem` 走现有 ingestion 管线**真实写入知识库**，作为闭环验证。

## 9. 里程碑建议

1. **M1 统一抽象**：统一生命周期接口 + manifest schema，把四类现有扩展点收敛为"内置插件"（不改行为）。
2. **M2 gRPC 装载**：外部插件通道 + `PluginManager`（发现/校验/拉起/健康检查/摘除）。
3. **M3 安全边界**：权限声明 + L1 受控出口 + L2 进程网络隔离 + 审计。
4. **M4 示例**：本地目录数据源外部插件，跑通完整同步 + 增量正确性 + 导入知识库。
5. **M5 脚手架与文档**：可复制模板 + 全套文档，供他人独立开发；CLI 作为后续增强。

## 10. 风险与开放问题

- gRPC 进程间方案下，增量同步的流式/断点续传语义在跨进程边界的**一致性**需重点设计（cursor 归属与幂等）。
- 网络隔离（L2）在桌面版/多平台部署上的落地方式需进一步验证（容器 vs 网络命名空间 vs 平台能力）。
- 插件版本升级与 `compatibility` 范围冲突时的回退策略需明确。
- 现有 Python docreader 的 RPC 自动发现先例，可作为跨语言外部插件（如 Python 插件）的参照扩展。
