# 检索引擎（Retriever）插件系统完整方案

> 状态：定稿版（综合四轮讨论）。核心结论与上一版一致，但修正了实例模型、Store 生命周期、Provider Registry、幂等与分数语义等关键细节。

---

## 0. 一句话方案

> 五类扩展共享统一控制面，但不强行共享同一种数据面运行形态。Retriever 将「宿主检索编排」与「向量库驱动」解耦：**内置驱动走进程内高性能路径，外部/不可信驱动走进程外 gRPC**，两种驱动通过同一个 `RetrieverBackend`（`RetrieveEngineRepository`）接口接入宿主。外部插件采用**共享 Runtime + store_handle** 的实例模型。

---

## 1. 架构定位：Retriever 为什么特殊

| 扩展点 | 状态性 | 数据流 | 形态 |
|---|---|---|---|
| DataSource | 弱状态（cursor 是书签） | 宿主拉取 | 进程外 gRPC |
| Parser / WebSearch / Model | 无状态 | 单次投喂 / 查询 | 进程外 gRPC |
| **Retriever** | **强状态（连接/Store/索引一致性）** | **双向持续（写 + 查）** | **双形态** |

关键澄清：向量数据**不在宿主内存**（在 PG/Qdrant/Milvus），宿主持有的是连接、连接池、`VectorStore` 配置、知识库绑定。这些状态**可通过协议管理**，进程外不是禁区；embedding 宿主算、向量跨进程传，**有性能成本但技术上可行**。

---

## 2. 核心概念：解耦 ≠ 独立

| 维度 | 解决问题 | 手段 |
|---|---|---|
| **解耦** | 新增驱动不改核心工厂 switch | Driver Registry |
| **独立** | 不改主仓、不重编译、隔离、独立升级 | 进程外 gRPC / OCI |

课题验收要的是"独立"。解耦（Driver Catalog）是宿主代码整理，不是插件系统的必要部分。

---

## 3. 插件边界：RetrieverBackend 接口

```text
宿主编排层（留宿主，绝不外置）
├── CompositeRetrieveEngine（组合 / 写广播 / 类型路由）
├── KeywordsVectorHybridService（embedding / 批处理 / 重试 / 并发）
├── RRF 融合 / EngineAwareNormalizer 归一化
├── 多 Store fan-out / rehydrate / storeGen
└── 租户绑定 / 知识库权限

插件边界（RetrieverBackend = RetrieveEngineRepository）
├── Save / BatchSave / Retrieve
├── DeleteByChunkIDList / DeleteBySourceIDList / DeleteByKnowledgeIDList
├── CopyIndices / BatchUpdateChunkEnabledStatus / BatchUpdateChunkTagID
└── EstimateStorageSize
```

插件只负责：调向量库 API、处理数据结构、执行 SQL、管理连接。

## 4. 双形态：内置进程内 + 外部 gRPC

```text
                    RetrieverBackend 接口
                           │
        ┌──────────────────┴──────────────────┐
        ▼                                     ▼
  内置进程内 Backend                     外部 gRPC Backend
  (Qdrant/Milvus/OpenSearch/...)         (第三方向量库插件)
  直接调 SDK，无序列化开销                 gRPC + ProcessRuntime
  性能最好，需重新编译宿主                 隔离/独立升级，不改主仓
```

| 场景 | 形态 |
|---|---|
| 内置向量库、高 QPS、大规模建索引 | 内置进程内 Driver |
| 第三方社区向量库、非 Go 后端 | 进程外 gRPC |
| 不可信插件、需隔离 | 进程外（Docker/OCI，见 §12 约束） |
| 需独立升级、独立发布 | 进程外 gRPC |

## 5. 实例模型：三分（关键修正）

上一版选"一 Store 一 Runtime"，**与 PluginManager 不兼容**——`PluginManager.entries` 以 `manifest.ID` 为唯一键，一个插件只能注册一个 Runtime（`runtime.go` 拒绝重复 ID）。支持"一 Store 一 Runtime"需把 `PluginID` 和 `RuntimeInstanceID` 拆开，属大改。

**定稿改为共享 Runtime + store_handle**，三个概念：

```text
1. Plugin Package（安装了什么）
   plugin_id = community.qdrant, engine_type = community_qdrant
   ← plugin.yaml

2. Plugin Runtime（正在运行的进程）
   community.qdrant (generation=4, state=running)
   ← PluginManager 管理，一个 plugin 一个 Runtime

3. Store Session（某个 VectorStore 在插件进程内的连接实例）
   store_id / store_handle(opaque) / runtime_generation
   ← 插件内部管理
```

```text
Plugin Package
      │
      ▼
Plugin Runtime（一个插件一个进程）
      ├── Store Session A（handle-a → Qdrant 集群 A 连接池）
      ├── Store Session B（handle-b → Qdrant 集群 B 连接池）
      └── Store Session C（handle-c → Milvus 集群 C 连接池）
```

**优点**：不改 PluginManager 唯一键、不改 Loader 启动模型、不改健康监督/Admission/Drain/Fencing、一个插件包只启动一个进程、符合 DataSource/Model 的共享 Runtime 模式。

## 6. 外部插件协议（含 Store 生命周期）

### 6.1 强类型向量（修正 Struct 传 embedding 的缺陷）

```protobuf
message RetrieverVector {
  repeated float values = 1;   // 强类型
}

message RetrieverRecord {
  RetrieverIndexInfo index_info = 1;
  RetrieverVector embedding = 2;  // 显式字段，不再塞 Struct
}

message RetrieverBatchUpsertRequest {
  string store_handle = 1;
  repeated RetrieverRecord records = 2;
  int32 dimensions = 3;           // 统一维度声明
  string operation_id = 4;        // 幂等键
}
```

插件必须校验：非空向量长度 == `dimensions`；关键词-only 写入允许 `embedding` 为空、`dimensions = 0`。

### 6.2 最小稳定 Service 定义

对外协议遵循“薄协议、能力可选”原则。核心接口只保留所有 Retriever 都绕不开的操作；重建、复制索引、深度健康检查等能力通过 capability 和可选接口扩展，不强迫每个插件实现。

```protobuf
service RetrieverPlugin {
  // v1 保留现有 wire 名称；SDK 可将其暴露为 Describe，避免业务代码依赖
  // EngineInfo 这一历史命名。
  rpc EngineInfo(RetrieverInfoRequest) returns (RetrieverInfoResponse);
  rpc OpenStore(RetrieverOpenStoreRequest) returns (RetrieverOpenStoreResponse);
  rpc CloseStore(RetrieverCloseStoreRequest) returns (RetrieverResponse);
  rpc StoreHealth(RetrieverStoreHealthRequest) returns (RetrieverStoreHealthResponse);

  rpc BatchUpsert(RetrieverBatchUpsertRequest) returns (RetrieverBatchUpsertResponse);
  rpc Retrieve(RetrieverRetrieveRequest) returns (RetrieverRetrieveResponse);
  rpc Delete(RetrieverDeleteRequest) returns (RetrieverResponse);
  rpc UpdateChunkState(RetrieverUpdateChunkStateRequest) returns (RetrieverResponse);
}
```

核心协议不直接出现 `CreateCollection`、`CreateTable`、`CreateIndexAlias` 等物理概念。插件可在 `OpenStore` 或首次 `BatchUpsert` 时自行创建所需结构。需要显式预建索引、无损重建、索引复制的插件，通过可选 capability 暴露 `EnsureIndex`、`BeginRebuild/CommitRebuild/AbortRebuild`、`CopyIndices`，宿主仅在插件声明支持时调用。

### 6.3 关键消息

```protobuf
message RetrieverOpenStoreRequest {
  string store_id = 1;
  google.protobuf.Struct connection_config = 2;  // 连接参数（可含敏感字段，宿主加密后注入）
  google.protobuf.Struct index_config = 3;
}
message RetrieverOpenStoreResponse {
  string store_handle = 1;              // 不透明、随机，不得等于 store_id / 地址
  repeated string capabilities = 2;     // vector / keywords
  RetrieverScoreProfile score_profile = 3;
  string error = 4;
}

message RetrieverInfoResponse {
  string engine_type = 1;
  repeated RetrieverCapability capabilities = 2;
  RetrieverScoreProfile score_profile = 3;
  RetrieverDimensionPolicy dimension_policy = 4;
  string config_schema_json = 5;
  RetrieverError error = 6;
}

message RetrieverRetrieveRequest {
  string store_handle = 1;
  string query = 2;
  repeated float embedding = 3;         // 强类型
  repeated string knowledge_base_ids = 4;
  int32 top_k = 5;
  double threshold = 6;
  string retriever_type = 7;            // vector / keywords
  google.protobuf.Struct additional_params = 8;
}

message RetrieverDeleteRequest {
  string store_handle = 1;
  repeated string ids = 2;
  RetrieverDeleteScope scope = 3;       // chunk / source / knowledge
  int32 dimension = 4;
  string knowledge_type = 5;
  string operation_id = 6;
}
```

`StoreHealth` 保留在核心 RPC 中，但 SDK 提供默认实现：只要 handle 存在且 Session 未关闭，就返回 `ready`。插件作者只有在需要探测真实后端连接时才实现可选的 `HealthChecker` 接口；因此核心协议具备 Store 级观测能力，同时不会增加最简插件的开发负担。

## 7. 幂等与批量失败语义

- 每个变更请求携带 `operation_id`；
- `BatchUpsert` 按稳定 Record ID 幂等；`Delete` 按稳定 ID 幂等；
- 同一 `operation_id` 重试不得重复产生副作用（插件去重，或声明后端天然幂等）；
- 批量写失败：第一版**整批成功或整批失败**；若后端会部分成功，响应携带：

```protobuf
message RetrieverItemError {
  string source_id = 1;
  string code = 2;
  bool retryable = 3;
  string message = 4;
}
```

## 8. 分数语义声明

当前 `EngineAwareNormalizer` 按引擎名硬编码 `switch engineType`。外部插件的 engine_type 对宿主是未知的，必须声明：

```protobuf
enum RetrieverScoreKind {
  SCORE_KIND_UNSPECIFIED = 0;
  SCORE_NORMALIZED_0_1 = 1;      // 相似度 [0,1]
  SCORE_SIGNED_COSINE = 2;       // cosine [-1,1]
  SCORE_DISTANCE_LOWER_BETTER = 3;
  SCORE_RANK_ONLY = 4;           // 无界分数，靠 rank
}

message RetrieverScoreProfile {
  RetrieverScoreKind vector_score_kind = 1;
  double distance_max = 2;
}
```

宿主按声明归一化，而不是为每个外部 engine_type 加 switch。

## 9. 接入层：拆两部分

### 9.1 External Retriever Provider Registry（必需，非可选）

宿主必须知道"哪些外部 Retriever 插件、每个对应什么 engine_type、配置 Schema、能力、分数语义、如何创建 Store Session"，否则 `validEngineTypes` 会拒绝未知类型、核心代码仍需 `if engineType == "community_qdrant"`。

```go
type ExternalRetrieverProvider struct {
    PluginID     string
    EngineType   types.RetrieverEngineType
    Name         string
    ConfigSchema map[string]any
    Capabilities []types.RetrieverType
    ScoreProfile ScoreProfile
}
```

第一版**不迁移内置 Driver**，只建外部 Provider 的最小注册目录；未来可和内置 Driver Catalog 合并。

### 9.2 Package Adapter（启动时，管"插件类型"）

```text
plugin.yaml → 校验 metadata.engine_type → EngineInfo → 注册 ExternalRetrieverProvider
```

不创建具体 Store。

### 9.3 Remote Engine Factory（创建/加载 Store 时，管"Store 实例"）

```text
VectorStore
   → ProviderRegistry.Get(engine_type)
   → OpenStore(store_id, connection_config, index_config)
   → store_handle
   → GRPCRetrieverRepository{store_handle, generation}
   → NewKVHybridRetrieveEngine(repository, engine_type)
   → RegisterWithStoreID
```

两个职责不能混在一起。

## 10. 重启与删除恢复

共享 Runtime 重启后，插件内存里的 `store_handle → client` 映射全部丢失。旧 `GRPCRetrieverRepository` 的 handle 不能继续用。

- 每个 Repository 绑定 Runtime generation，调用前校验，旧代返回 `stale runtime error`（复用 DataSource Proxy 的 generation 模式）；
- 恢复复用现有 `GetOrLoadByStoreID`：发现旧 Repository 不可用 → EngineFactory 按 VectorStore 配置重新 OpenStore → 新 handle → 新 Repository → `registerIfGenUnchanged`。

现有 Registry 已具备 singleflight / 构建超时 / 失败冷却 / storeGen，无需重做。

**注意**：Plugin Runtime 的 generation（防旧进程结果提交）和 Retriever Registry 的 storeGen（防旧 Store 构建覆盖新实例）是**两层不同的 fencing**，都要说明。

---

## 11. 健康检查：Plugin Health vs Store Health

- `PluginControl.Health` = 进程级健康（进程活着、gRPC 响应）；
- `StoreHealth(store_handle)` = Store 实例级健康，状态：`ready / degraded / unavailable / closed`。

**不能**因为一个 Store 连接失败就把整个共享 Runtime 判 unhealthy 并重启（否则 Store A 配置错误会拖垮 Store B/C）。

---

## 12. 受控 egress 约束（明确边界）

`DockerRuntime` 目前只支持 `network: none`，非 none 直接拒绝启动。而真实 Retriever 插件必须联网（Qdrant/Milvus/OpenSearch）。

| 模式 | 能否运行联网 Retriever |
|---|---|
| ProcessRuntime | ✅ 可以（开发验证） |
| DockerRuntime + network none | ❌ 不可以 |
| DockerRuntime + 受控 egress | ❌ 尚未完成 |

**第一阶段结论**：完成外部 Retriever 的协议与 ProcessRuntime 闭环；生产级 OCI 联网运行依赖受控 egress runtime，作为后续前置工作。

## 13. 课题定位（不过度拔高）

课题验收明确要求的是**示例 DataSource 插件**完成数据同步。Retriever 的背景痛点是"新增向量库要改核心工厂文件"。

Retriever 的最低有效成果：统一控制面已预留 retriever + 业务协议已定义 + 核心工厂耦合有明确解法 + 新增 Retriever 不影响 PluginManager/Runtime。**把 Retriever 做成真正的外部插件是有价值的加分项，但不是验收前提。** 不要让 Retriever 的复杂度拖住 DataSource 示例、权限隔离、开发文档等明确验收项。

## 14. 完整运作流程

```text
① 宿主启动
   ↓
② 扫描 Retriever 插件目录（WEKNORA_PLUGIN_DIR_RETRIEVER）
   ↓
③ 启动每个 Retriever Provider Runtime（一个插件一个进程）
   ↓
④ Handshake + EngineInfo
   ↓
⑤ 注册 ExternalRetrieverProvider（engine_type → descriptor + runtime ref）
   ↓
⑥ 前端从 Provider Registry 取可选 engine_type + config_schema
   ↓
⑦ 用户创建 VectorStore
   ↓
⑧ Remote Engine Factory 调 OpenStore
   ↓
⑨ 获得 store_handle
   ↓
⑩ 创建 GRPCRetrieverRepository
   ↓
⑪ RegisterWithStoreID
```

运行阶段：

```text
宿主 embedding / Composite / RRF / 权限
   ↓
GRPCRetrieverRepository（强类型 BatchUpsert / Retrieve）
   ↓
外部 Retriever Runtime
   ↓
具体向量数据库
```

## 17. 结论

> Retriever 是能做成插件的，且是五类扩展里唯一需要"双形态"的。正确方案：宿主编排层留进程内，驱动层抽成 `RetrieverBackend` 接口；内置驱动进程内，外部/不可信驱动进程外 gRPC。外部插件协议必须做对四件事——**强类型向量、Store 生命周期（OpenStore/store_handle）、幂等语义、分数语义声明**。实例模型采用**共享 Runtime + store_handle**（与 PluginManager 唯一键模型兼容），接入层拆 **Provider Registry + Package Adapter + Remote Engine Factory** 三部分，恢复复用现有 generation + storeGen 双层 fencing。

## 18. 插件作者体验：最终应该怎样制作

### 18.1 区分最终用户和插件开发者

本方案面对两类人：

| 用户 | 需要做什么 | 不应该接触什么 |
|---|---|---|
| WeKnora 使用者 | 安装插件、填写配置、创建 VectorStore、绑定知识库 | gRPC、`store_handle`、KVHybrid、RRF、租户校验 |
| Retriever 插件开发者 | 对接自己的向量库、填写 Manifest、通过一致性测试 | WeKnora 的 `internal/` 包、宿主数据库表、检索编排代码 |

“复杂的东西让插件用户来做”应理解为：**复杂的后端适配由插件开发者负责，系统级安全和一致性由宿主负责；最终使用者不需要承担框架复杂度。**

### 18.2 当前低层协议直接交给开发者并不顺利

如果开发者直接阅读 `plugin.proto` 并自行实现全部 gRPC 服务，他还需要理解：

```text
Protobuf 编解码、Store handle 映射、多个 Store Session、错误编码、超时和取消、幂等重试、维度校验，以及 WeKnora 内部 IndexInfo 和 RetrieveResult。
```

这会使“实现一个向量库插件”变成“实现一个小型 WeKnora 适配框架”。因此最终交付不能只有 proto，必须提供 **薄协议 + 厚 SDK + 一致性测试工具**。

### 18.3 最简插件的目标体验

一个只支持向量检索的插件，理想上只需要：

```text
1. 复制 Retriever 模板
2. 填写 plugin.yaml
3. 实现 OpenBackend(config)
4. 实现 BatchUpsert
5. 实现 Retrieve
6. 实现 Delete
7. 实现 UpdateChunkState
8. 运行 conformance test
9. 构建并安装插件包
```

以下工作应由 SDK 或宿主自动完成：

```text
PluginControl 注册、Handshake / Health、gRPC Service 注册、Store Session 表、store_handle 生成和失效、请求/响应转换、标准错误包装、InvocationContext、deadline / cancellation 和 Runtime generation 校验。
```

## 19. IDEA 式模型：Provider 无状态，StoreSession 有状态

本方案借鉴 IDEA 的扩展点思想，但不复制其具体实现：

```text
Plugin Package
    └── plugin.yaml
          ↓
Retriever Provider
    └── 身份、能力、配置 Schema
          ↓
Retriever StoreSession
    └── 一个 VectorStore 的连接、连接池和索引状态
          ↓
Backend Implementation
    └── 具体向量数据库 SDK 和实现细节
```

必须遵守：

```text
Provider 尽量无状态
StoreSession 承担连接和索引状态
不把数据库 Client 放进包级变量
不在 init() 中建立连接
不让插件依赖宿主 internal 包
```

这样一个插件可以服务多个 VectorStore，又不会把多个 Store 的连接和凭证混在一起。Runtime 重启后，宿主只需重新调用 `OpenStore`，插件即可重建 StoreSession。

## 20. 面向开发者的稳定 SDK，而不是暴露宿主内部接口

当前 `internal/types/interfaces/retriever.go` 中的 `RetrieveEngineRepository` 适合作为宿主内部适配边界，但不应成为外部插件作者的长期 API。外部插件只依赖发布后的 `pkg/pluginapi` SDK。

SDK 对外建议提供以下抽象：

```go
type RetrieverBackendFactory interface {
    OpenBackend(ctx context.Context, config StoreConfig) (RetrieverBackend, error)
}

type RetrieverBackend interface {
    BatchUpsert(ctx context.Context, request BatchUpsertRequest) error
    Retrieve(ctx context.Context, request RetrieveRequest) (RetrieveResponse, error)
    Delete(ctx context.Context, request DeleteRequest) error
    UpdateChunkState(ctx context.Context, request UpdateChunkStateRequest) error
}
```

SDK 内部负责把 `OpenBackend` 包装成 `OpenStore`，把 Backend 包装成 gRPC Handler，把随机 handle 映射到 StoreSession，再由宿主侧 `GRPCRetrieverRepository` 适配回当前的 `RetrieveEngineRepository`。

因此未来即使宿主内部把：

```text
RetrieveEngineRepository 拆成 VectorWriter / VectorReader / IndexLifecycle
```

外部插件仍然只需要面对稳定的后端语义；变化被宿主的 Proxy 和 Adapter 吸收。

## 21. 宿主与插件责任边界

### 21.1 宿主负责系统级不变量

宿主必须统一保证：

```text
插件身份和协议版本正确
Manifest 能力与运行时能力一致
VectorStore 属于当前租户
KnowledgeBase 绑定关系合法
请求带 deadline 和取消信号
调用受 Admission Control 约束
旧 generation 不能继续提交结果
Runtime 重启后可以重新建立 StoreSession
敏感配置不进入日志和普通响应
```

### 21.2 插件负责后端实现和语义兑现

插件必须保证：

```text
稳定 Record ID 不产生重复记录
相同 operation_id 重试不会重复产生副作用
旧 revision 不覆盖新 revision
维度不匹配明确失败
Delete 是幂等的
UpdateChunkState 失败必须返回错误
声明支持的能力真实可用
返回 score 符合 ScoreProfile
```

插件可以自由决定：

```text
使用原生 Upsert 还是数据库事务
使用 collection、table 还是 index
一维度一集合还是单表混维
如何创建和迁移索引
如何连接池复用
如何重试后端请求
如何实现 BM25 或 ANN
```

协议规定的是**结果语义**，不规定插件内部必须采用哪种数据库操作。
