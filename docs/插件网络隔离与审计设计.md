# 插件网络隔离与审计设计（验收标准二）

> 目标：满足课题一验收标准二——"插件声明不联网时，运行期实际无法发起出站请求，尝试联网会被拦截并记录"。
> 本文档记录**最终落地方案**：SDK 侧 Guarded Client 拦截 + stderr 结构化日志审计 + 宿主捕获记录。代码已实现并测试通过。

---

## 1. 方案总览：三层协作

```text
┌──────────────────────────────────────────────────────────┐
│ 第 1 层：SDK 侧 Guarded Client（拦截 + 写审计到 stderr）     │
│   pkg/pluginapi/guarded_client.go                         │
│   在 Dial 层：拦截(return err) + 写 plugin_audit(到 stderr) │
├──────────────────────────────────────────────────────────┤
│ 第 2 层：运行时硬隔离（不可绕过的拦截）                      │
│   DockerRuntime --network none：物理断网，兜底              │
│   保证即使插件绕过 SDK 的 client，也实际出不去               │
├──────────────────────────────────────────────────────────┤
│ 第 3 层：宿主捕获 + 解析 + 落盘（记录的可观测性）             │
│   StderrPipe 捕获 → ParseAuditLine 解析补身份               │
│   → AsyncAuditSink 异步落盘（有界队列，满则丢弃计数）         │
└──────────────────────────────────────────────────────────┘
```

**设计原则**：
1. **拒绝强制、审计 best effort**——拦截（return err）是硬保证，写审计失败不影响拒绝；
2. **宿主补身份**——插件自报的 `plugin_id` 不可信，由宿主用 Manifest ID 覆盖；
3. **异步背压**——审计落盘慢不能反过来拖死插件进程。

---

## 2. 第 1 层：SDK 侧 Guarded Client

### 2.1 核心接口（已实现于 `pkg/pluginapi/guarded_client.go`）

```go
type NetworkPolicy string

const (
    NetworkNone      NetworkPolicy = "none"      // 禁止一切出站
    NetworkEgress    NetworkPolicy = "egress"    // 允许公网，禁 loopback/私网/link-local
    NetworkAllowlist NetworkPolicy = "allowlist" // 只允许白名单 host
)

// 显式构造受控 client（测试/特殊场景用）
func NewGuardedHTTPClient(policy NetworkPolicy, allowlist []string) *http.Client

// 从环境变量读宿主注入的策略（插件业务代码应使用这个）
func NewPluginHTTPClient() *http.Client
```

### 2.2 拦截 + 审计在同一逻辑路径

`net.Dialer` 的 `DialContext` 钩子里，拦截和写审计在**同一个判断分支**：

```go
func (g *networkGuard) check(address string) error {
    // ... 根据 policy 判断是否允许 ...
    if reason == "" {
        return nil                    // 允许
    }
    g.emitAudit(address, reason)      // ① 写审计（best effort）
    return fmt.Errorf("plugin network blocked: %s", reason)  // ② 拒绝（强制）
}
```

**关键**：`emitAudit` 写 stderr 失败不影响 `return error` 拒绝——拒绝是强制的，审计是尽力而为。

### 2.3 策略注入（策略由宿主决定，插件无法撒谎）

宿主在启动插件时注入环境变量（`process_runtime.go` / `docker_runtime.go`）：

```text
WEKNORA_PLUGIN_NETWORK_POLICY=none|egress|allowlist
WEKNORA_PLUGIN_NETWORK_ALLOWLIST=api.github.com:443,...
```

SDK 侧通过 `PolicyFromEnv()` / `AllowlistFromEnv()` 读取，`NewPluginHTTPClient()` 自动配置。**插件业务代码不硬编码策略**，策略来自宿主 manifest 的 `permissions.network`，插件无法通过改自己代码绕过声明。

## 3. 审计传输：stderr 单行 JSON

### 3.1 为什么用 stderr 而不是 gRPC 反向通道

审计是"插件 → 宿主"方向，而现有 gRPC 是"宿主 = client 调插件 = server"的**单向**拓扑。要"插件主动上报"，需要额外起反向 gRPC server（第二个监听端口），复杂度高。

**P0 采用 stderr 方案**：插件往标准错误输出写结构化日志，宿主通过 `cmd.StderrPipe()` 捕获。拓扑不变、无需反向通道、实现简单。

> 注：早期方案曾考虑"宿主拥有的 Audit RPC"，但该 RPC 若定义在插件 service 里会导致调用方向相反（宿主→插件），已废弃。若未来需要"不可伪造"的审计，再单独引入反向 `PluginAudit` service 或内核层观测。

### 3.2 协议格式（`AuditPrefix = "plugin_audit "`）

插件 SDK 拦截时，向 stderr 写**单行** JSON，前缀 `plugin_audit `：

```text
plugin_audit {"action":"network_denied","destination":"example.com:443","policy":"none","reason":"outbound network is disabled","timestamp":"2026-08-22T13:48:43Z"}
```

协议约定：

- 一条事件独占一行；
- 固定 `plugin_audit ` 前缀；
- 后面是**单行** JSON（不换行、reason 里的换行由 JSON 转义）；
- 单条行长度上限 64 KiB（`scanner.Buffer`）；
- 解析失败按普通日志透传，不影响插件运行；
- **插件侧不写 `plugin_id`**（自报身份不可信），由宿主补。

## 4. 第 2 层：DockerRuntime 硬隔离（已有，兜底）

`docker_runtime.go` 的 `--network none` 物理断网，配合 `--read-only --cap-drop ALL --no-new-privileges --pids-limit 128`：

- 插件用 SDK client → 第 1 层拦截 + 记录；
- 插件绕过 SDK 直接 `net.Dial` → 第 2 层 `--network none` 让连接失败（此路径记录不到，见第 6 节边界）。

---

## 5. 第 3 层：宿主捕获 + 解析 + 落盘

### 5.1 捕获（两个 Runtime 均已接入）

```go
// process_runtime.go / docker_runtime.go
stderr, _ := cmd.StderrPipe()          // 接管插件 stderr
go ConsumePluginStderr(stderr, r.Manifest.ID, r.AuditSink)  // 异步消费
```

`NewProcessRuntime` 和 `NewDockerRuntime` 默认安装 `LoggerAuditSink`，所以经
Loader 创建的 Runtime 不会丢弃 `plugin_audit`；宿主会把结构化事件写入主程序
日志。部署方可以替换 `AuditSink`，例如包一层 `AsyncAuditSink` 接入文件或
数据库。当前代码没有假装提供一个未实现的内置 `FileAuditSink`。

### 5.2 解析补身份（`internal/plugin/security.go`）

```go
// ParseAuditLine 识别 plugin_audit 前缀 → 解析 JSON → 用宿主 pluginID 覆盖身份
func ParseAuditLine(line, pluginID string) (AuditEvent, bool)

// ConsumePluginStderr 逐行读：审计行进 sink，普通日志原样透传
func ConsumePluginStderr(pipe io.Reader, pluginID string, sink AuditSink)
```

`AuditEvent`（宿主侧，比插件侧多了 `PluginID`/`Allowed` 字段）：

```go
type AuditEvent struct {
    PluginID    string    `json:"plugin_id"`    // 宿主填，不信任插件
    Action      string    `json:"action"`
    Destination string    `json:"destination"`
    Allowed     bool      `json:"allowed"`      // 被拦的都是 false
    Reason      string    `json:"reason"`
    Policy      string    `json:"policy"`
    At          time.Time `json:"at"`
}
```

### 5.3 异步写入（有界队列，防止慢速 sink 拖死插件）

`AsyncAuditSink` 实现 `AuditSink` 接口，内部有界队列 + 后台 worker：

```go
async := NewAsyncAuditSink(fileSink, 1024)   // 队列满则丢弃 + 计数
```

- 队列满 → **丢弃 + 计数**（`Dropped()` 可查），绝不阻塞 stderr 消费；
- 丢审计 ≠ 丢安全：拦截由 `--network none` 硬保证，审计 sink 是 best effort 记录；
- 队列满本身是异常信号（插件在异常速率联网），生产可接告警。

`AuditSink` 是接口，现有 `MemoryAuditSink`（测试用）和默认
`LoggerAuditSink`（生产主程序日志）；部署方可自行替换为 JSONL 文件或数据库
sink，插件侧和解析侧无需改动。

## 6. 验收场景（对齐标准二，分两组）

### 组 A：SDK 合规插件（验证"拦截 + 记录"闭合）

```text
1. manifest 声明 permissions.network = none
2. 宿主注入 WEKNORA_PLUGIN_NETWORK_POLICY=none
3. 插件用 NewPluginHTTPClient() 访问 https://example.com
4. 预期：
   a. Dial 层拦截 → 返回 network blocked（请求失败）
   b. 同一处写 plugin_audit 到 stderr
   c. 宿主 StderrPipe 捕获 → 解析补 plugin_id → AuditSink 收到
```

### 组 B：绕过 SDK 的插件（验证"实际无法出站"）

```text
1. manifest 声明 permissions.network = none
2. 插件绕过 SDK 直接 net.Dial 访问 1.2.3.4:443
3. DockerRuntime --network none 启动
4. 预期：连接失败（物理无法出站）；不要求记录（内核层观测属后续加固）
```

## 7. 诚实边界声明

| 场景 | 拦截 | 记录 | 说明 |
|---|---|---|---|
| 插件用 SDK 的 Guarded client | ✅ | ✅ | 拦截与审计在同一逻辑路径（第 1 层） |
| 插件绕过 SDK 直接 `net.Dial` | ✅（`--network none`） | ❌ | 硬隔离拦得住，但宿主当前无法观测"尝试" |
| `ProcessRuntime` 开发态 | ❌ | 仅 SDK 层 | 明确不承诺安全隔离 |

**精确表述**：

> 对使用 SDK Guarded Client 的网络请求，拦截和审计在同一逻辑路径完成；对绕过 SDK 的原始 socket 请求，Docker/OCI 负责硬隔离（实际无法出站），完整观测需要后续引入 nftables、NFLOG 或 eBPF。

## 9. 结论

验收标准二的正确解法是**让拦截和记录在同一层闭合，同时用运行时硬隔离兜底**：

- SDK Guarded Client（第 1 层）：拦截 + 写 `plugin_audit` 到 stderr，拒绝强制、审计 best effort；
- DockerRuntime `--network none`（第 2 层）：不可绕过的硬兜底；
- 宿主捕获 + 解析 + 异步落盘（第 3 层）：让记录可查询、可验收，且不会被慢速落盘拖死。

该方案已完整落地并通过单元 + 集成测试，剩余工作为落盘实现、Docker 真实验收和可选的内核层加固。
